KaraAPI

KaraAPI is a modern Paper plugin API/framework designed to make plugin development cleaner, faster, and more structured.

It provides a central runtime that bootstraps host plugins and exposes lifecycle-aware services for commands, listeners, tasks, configs, messages, placeholders, storage, registries, profiles, custom items, requirements, regions, UI, scheduler execution, recipes, and effects.

KaraAPI manages the runtime.
The host plugin owns its commands, listeners, tasks, configs, messages, items, regions, recipes, effects, and services.
Documentation notice

These docs are meant to help understand and use KaraAPI, but they may be outdated or incomplete.

The actual source code is always the source of truth. If something in the documentation conflicts with the implementation, follow the code in:

src/main/java/org/kerix/karaapi

Before relying on an API, class, method, package, or example, always verify it against the current repository source.

Features

  • Central bootstrapping through KaraAPI.boot(...)
  • Per-host-plugin PluginHandle
  • Lifecycle-aware ServiceContainer
  • Startable, Stoppable, and Tickable interfaces
  • Tick orchestrator grouped by tick interval
  • Task API with default and named task groups
  • Scheduler abstraction with sync, async, delayed, timer, location, entity, and Folia-aware execution hooks
  • Config API for plugin-owned YAML files
  • Message API with local placeholders, gradients, MiniMessage rendering, and optional PlaceholderAPI resolution
  • Placeholder service with local providers and optional PlaceholderAPI expansion registration
  • Registry API for ID-based plugin content
  • Storage/repository API for persistent plugin data
  • Profile cache API
  • Command tree API with requirements, suggestions, typed arguments, and nested commands
  • Menu/inventory GUI API, including paginated menus
  • Item builders, written book builder, skull builder, item keys, and custom item API
  • UI helpers for chat, action bar, titles, boss bars, and sidebars
  • Color and gradient utilities
  • Requirement API
  • Region API
  • Typed event bus
  • Effect API for described particles, sounds, ambient sounds, geometry, motifs, and handles
  • Recipe API for shaped and shapeless recipe definitions
  • Internal Paper adapter layer kept separate from public API

Compatibility

The current main branch targets modern Paper plugin development.

Java 21
Paper API 1.21.1-R0.1-SNAPSHOT
Minecraft API version 1.21
PlaceholderAPI as an optional soft dependency

The build uses a Java 21 toolchain and compiles against Paper API and PlaceholderAPI as compile-only dependencies.

Folia-aware behavior is exposed through SchedulerService and the scheduler executor abstraction. Normal host plugins should use context.scheduler() or context.tasks() instead of depending on raw Bukkit scheduler calls.

Installing KaraAPI as a Dependency

KaraAPI is installed as a server plugin. Host plugins declare a dependency on KaraAPI and then boot their own handle during onEnable().

KaraAPI plugin.yml

name: KaraAPI
version: '${version}'
main: org.kerix.karaapi.KaraAPIPlugin
api-version: '1.21'
authors:
  - Kerix
description: Core API library for Kara plugins.
load: STARTUP
softdepend:
  - PlaceholderAPI

Host plugin plugin.yml

A plugin that uses KaraAPI should depend on it:

name: ExamplePlugin
version: '1.0.0'
main: com.example.exampleplugin.ExamplePlugin
api-version: '1.21'

depend:
  - KaraAPI

commands:
  example:
    description: Example command
    usage: /example

If your host plugin also directly uses PlaceholderAPI behavior, add PlaceholderAPI as a soft dependency in your own plugin.

Gradle Setup

Step 1. Add repositories in settings.gradle.kts:

pluginManagement {
    repositories {
        gradlePluginPortal()
        maven("https://repo.papermc.io/repository/maven-public/")
    }
}

dependencyResolutionManagement {
    repositoriesMode.set(RepositoriesMode.FAIL_ON_PROJECT_REPOS)
    repositories {
        mavenCentral()
        maven("https://repo.papermc.io/repository/maven-public/")
        maven("https://repo.extendedclip.com/content/repositories/placeholderapi/")
        maven("https://jitpack.io")
    }
}

Step 2. Add KaraAPI as a dependency in build.gradle.kts. Because KaraAPI is installed as a plugin on the server, host plugins should normally use compileOnly:

dependencies {
    compileOnly("com.github.Karalium:KaraAPI:<tag>")
}

Replace <tag> with the release tag you want to use.

Avoid shading KaraAPI into host plugins unless you intentionally want a different deployment model. The normal model is: KaraAPI jar in plugins/, host plugin depends on KaraAPI.

Bootstrapping a Host Plugin

A host plugin should be small. It delegates service creation and feature registration to KaraAPI modules.

package com.example.exampleplugin;

import org.bukkit.plugin.java.JavaPlugin;
import org.kerix.karaapi.api.KaraAPI;
import org.kerix.karaapi.api.PluginHandle;

public final class ExamplePlugin extends JavaPlugin {

    private PluginHandle handle;

    @Override
    public void onEnable() {
        this.handle = KaraAPI.boot(
                this,
                new CoreModule(),
                new CommandModule(),
                new ListenerModule(),
                new PlaceholderModule()
        );
    }

    @Override
    public void onDisable() {
        if (handle != null) {
            handle.shutdown();
            handle = null;
        }
    }
}

The returned PluginHandle owns the host plugin runtime. Store it and always shut it down.

Plugin Modules

Modules are where you register services, commands, listeners, messages, items, profiles, recipes, effects, and other systems.

package com.example.exampleplugin;

import org.kerix.karaapi.api.bootstrap.BootstrapContext;
import org.kerix.karaapi.api.bootstrap.PluginModule;

public final class CoreModule implements PluginModule {

    @Override
    public void configure(BootstrapContext context) {
        context.hostPlugin().getLogger().info("Configuring core systems...");

        context.configs().main();
        context.configs().config("messages.yml");

        context.tasks().timer("heartbeat", 20L, 20L, () -> {
            context.announcer().info("Heartbeat");
        });
    }
}

A good host plugin usually has multiple small modules: commands, listeners, menus, items, recipes, effects, storage, and gameplay systems.

You can also retrieve bound services through the service container:

MyService service = context.service(MyService.class);

PluginHandle

PluginHandle is the host plugin's runtime handle after boot. It exposes the host plugin, the bootstrap context, service lookup, service accessors, and shutdown.

PluginHandle handle = KaraAPI.boot(this, new CoreModule());

handle.hostPlugin();
handle.context();
handle.commands();
handle.listeners();
handle.tasks();
handle.scheduler();
handle.menus();
handle.messages();
handle.placeholders();
handle.recipes();
handle.effects();

handle.shutdown();

The current main branch exposes effects() directly on PluginHandle as well as on BootstrapContext.

ServiceContainer

ServiceContainer is KaraAPI’s dependency/lifecycle container. It replaces the older service-registry wording to avoid confusion with RegistryService.

context.services().bind(MyService.class, new MyService());

MyService service = context.services().get(MyService.class);

context.services().find(MyOptionalService.class).ifPresent(MyOptionalService::warmup);

Services may implement lifecycle interfaces:

import org.kerix.karaapi.api.lifecycle.Startable;
import org.kerix.karaapi.api.lifecycle.Stoppable;
import org.kerix.karaapi.api.lifecycle.Tickable;

public final class MyService implements Startable, Stoppable, Tickable {

    @Override
    public void start() {
        System.out.println("Started");
    }

    @Override
    public void stop() {
        System.out.println("Stopped");
    }

    @Override
    public long tickInterval() {
        return 20L;
    }

    @Override
    public void tick() {
        System.out.println("Tick every second");
    }
}

When a bound service implements Startable, Tickable, or Stoppable, KaraAPI can start it, register it with the tick orchestrator, and stop it during shutdown.

Task API

Use TaskService instead of directly calling Bukkit’s scheduler. It delegates execution to SchedulerService and tracks tasks for cleanup.

context.tasks().sync(() -> {
    player.sendMessage("Runs on the main thread");
});

context.tasks().async(() -> {
    // async work
});

context.tasks().later(20L, () -> {
    player.sendMessage("Ran one second later");
});

context.tasks().timer(0L, 20L, () -> {
    player.sendMessage("Runs every second");
});

Named tasks help debugging and cleanup:

context.tasks().timer("scoreboard", 0L, 20L, () -> {
    // update scoreboard
});

Task groups let you cancel feature-specific work together:

context.tasks().group("lobby").timer("scoreboard", 0L, 20L, () -> {
    // update lobby scoreboard
});

context.tasks().group("lobby").timer("announcer", 0L, 100L, () -> {
    // lobby announcement
});

context.tasks().cancelGroup("lobby");

Tick API

Use Tickable for lifecycle services that need regular ticking. Tickables make their interval explicit.

public final class LobbyTicker implements Tickable {

    @Override
    public long tickInterval() {
        return 20L;
    }

    @Override
    public void tick() {
        // runs every 20 ticks
    }
}

Bind it as a service:

context.services().bind(LobbyTicker.class, new LobbyTicker());

KaraAPI groups tickables by interval so tickables with the same interval can share scheduling work.

Scheduler API

SchedulerService is the lower-level scheduler abstraction used by the task service and systems like effects.

ScheduledTaskHandle sync = context.scheduler().sync(() -> {
    // main-thread work
});

ScheduledTaskHandle delayed = context.scheduler().later(20L, () -> {
    // delayed work
});

ScheduledTaskHandle timer = context.scheduler().timer(0L, 20L, () -> {
    // repeating work
});

ScheduledTaskHandle async = context.scheduler().async(() -> {
    // async work
});

ScheduledTaskHandle atLocation = context.scheduler().at(location, () -> {
    // location/region-aware work when supported
});

ScheduledTaskHandle onEntity = context.scheduler().entity(entity, () -> {
    // entity-aware work when supported
});

timer.cancel();

Use context.scheduler().folia() to check whether the active executor is Folia-aware.

Config API

Use ConfigService for plugin-owned YAML files.

YamlConfig config = context.configs().main();

YamlConfig messages = context.configs().config("messages.yml");
YamlConfig arenas = context.configs().config("arenas/spawn.yml");

context.configs().reloadAll();
context.configs().saveAll();

Typed keys keep config access clean:

public final class MyConfigKeys {

    public static final ConfigKey<String> SERVER_NAME =
            ConfigKey.string("server.name", "Kara Server");

    public static final ConfigKey<Integer> MAX_PLAYERS =
            ConfigKey.integer("server.max-players", 100);

    private MyConfigKeys() {
    }
}
String serverName = config.get(MyConfigKeys.SERVER_NAME);
int maxPlayers = config.get(MyConfigKeys.MAX_PLAYERS);

config.set(MyConfigKeys.SERVER_NAME, "New Server Name");
config.save();
Method Use
main()Loads or returns config.yml.
config(fileName)Loads or returns a named YAML config.
config(fileName, resourcePath)Loads a named YAML config with a separate bundled resource path.
get(fileName)Returns a loaded config or throws if it is missing.
loaded(fileName)Checks whether a config is already loaded.
reloadAll()Reloads every loaded config.
saveAll()Saves every loaded config.
unload(fileName, save)Unloads a config and optionally saves it.

Message API

Messages are loaded through MessageService. The main message bundle uses messages.yml.

prefix: "<gray>[<aqua>Kara</aqua>]</gray>"

messages:
  welcome: "<prefix> <green>Welcome, <player>!</green>"
  coins: "<prefix> <yellow>You have <coins> coins.</yellow>"
  gradient: "<gradient:#00ffaa:#ff00ff>Hello <player></gradient>"
  papi: "<prefix> <gray>Server online: %server_online%</gray>"

Define keys:

public final class MyMessages {

    public static final MessageKey WELCOME = MessageKey.of(
            "messages.welcome",
            "<prefix> <green>Welcome, <player>!</green>"
    );

    public static final MessageKey COINS = MessageKey.of(
            "messages.coins",
            "<prefix> <yellow>You have <coins> coins.</yellow>"
    );

    private MyMessages() {
    }
}

Send a message:

context.messages().send(
        player,
        MyMessages.WELCOME,
        PlaceholderSet.empty().add("player", player.getName())
);

Render a component directly:

Component component = context.messages().component(
        player,
        "<gradient:#00ffaa:#ff00ff>Hello <player>, online: %server_online%</gradient>",
        PlaceholderSet.empty().add("player", player.getName())
);

Rendering order

raw text
→ local placeholders
→ PlaceholderAPI placeholders, if PlaceholderAPI is installed
→ MiniMessage tags and gradients
→ Adventure Component

This means local placeholders and PlaceholderAPI placeholders can be embedded inside MiniMessage text before it is parsed into a component.

Placeholder API

KaraAPI has its own placeholder system that works even if PlaceholderAPI is not installed.

PlaceholderSet placeholders = PlaceholderSet.empty()
        .add("player", player.getName())
        .add("coins", 250);

Component component = context.messages().component(
        player,
        "<green>Hello <player>, coins: <coins></green>",
        placeholders
);

Local placeholder sets replace both angle and percent-style local forms where supported by the provider implementation.

<player>
<coins>
%player%
%coins%

PlaceholderAPI support

If PlaceholderAPI is installed, KaraAPI can also resolve external placeholders such as:

%player_name%
%server_online%
%vault_eco_balance%

If PlaceholderAPI is absent, local placeholders still work. External PlaceholderAPI placeholders are not resolved.

Creating PlaceholderAPI Expansions

Host plugins can register PlaceholderAPI expansions through KaraAPI. Use the public PlaceholderExpansion builder.

public final class PlaceholderModule implements PluginModule {

    @Override
    public void configure(BootstrapContext context) {
        PlaceholderExpansion expansion = PlaceholderExpansion
                .expansion(context.hostPlugin(), "example")
                .placeholder("name", player -> player == null ? "" : player.getName())
                .placeholder("online", player -> String.valueOf(player != null && player.isOnline()))
                .placeholder("coins", "250")
                .placeholder("rank", "Admin")
                .build();

        context.placeholders().registerExpansion(expansion);
    }
}

This creates PlaceholderAPI placeholders:

%example_name%
%example_online%
%example_coins%
%example_rank%
In the current main branch, registering an expansion through PlaceholderService requires PlaceholderAPI to be installed and available. Local placeholders do not require PlaceholderAPI.

Color and Gradient API

Create gradient components directly with ColorGradient:

Component component = ColorGradient.of("#00ffaa", "#ff00ff")
        .component("Gradient Text");

Generate MiniMessage gradient-like output:

String mini = ColorGradient.of("#00ffaa", "#ff00ff")
        .miniMessage("Gradient Text");

Or use MiniMessage gradient syntax through the message renderer:

Component component = context.messages().component(
        player,
        "<gradient:#00ffaa:#ff00ff>Hello <player></gradient>",
        PlaceholderSet.empty().add("player", player.getName())
);

Command API

Commands are built using command nodes. Use Commands.command(...) or CommandBuilder.command(...).

public final class CommandModule implements PluginModule {

    @Override
    public void configure(BootstrapContext context) {
        context.commands().register(
                Commands.command("example")
                        .usage("/example <reload|coins>")
                        .permission("example.use")

                        .then(Commands.command("reload")
                                .permission("example.reload")
                                .executes(ctx -> {
                                    context.configs().reloadAll();
                                    context.messages().reloadAll();
                                    return CommandResult.message("Reloaded.");
                                }))

                        .then(Commands.command("coins")
                                .playerOnly()
                                .executes(ctx -> {
                                    ctx.player().sendMessage("You have 250 coins.");
                                    return CommandResult.success();
                                }))

                        .build()
        );
    }
}

Suggestions are attached to the command builder:

.suggests((ctx, current) -> context.hostPlugin()
        .getServer()
        .getOnlinePlayers()
        .stream()
        .map(Player::getName)
        .toList())

Typed Command Arguments

The command API has typed argument schemas. Prefer typed arguments over manual string parsing when a command has structured input.

context.commands().register(
        Commands.command("givecoins")
                .playerOnly()
                .argument("target", Arguments.player())
                .argument("amount", Arguments.integer())
                .greedyArgument("reason")
                .executes(ctx -> {
                    Player target = ctx.player("target");
                    int amount = ctx.integer("amount");
                    String reason = ctx.string("reason");

                    target.sendMessage("You received " + amount + " coins. Reason: " + reason);
                    return CommandResult.success();
                })
                .build()
);

Common argument categories include text, numbers, booleans, players, offline players, worlds, materials, enums, choices, and greedy text.

Menu API

Create inventory GUIs without manually handling inventory events. Menus are definitions opened through MenuService.

Menu menu = Menu.builder(
        ColorGradient.of("#00ffaa", "#00ffff").component("Shop"),
        3
).border(
        ItemBuilder.of(Material.GRAY_STAINED_GLASS_PANE)
                .name(Component.empty())
                .build()
).slot(
        11,
        ItemBuilder.of(Material.DIAMOND_SWORD)
                .name(ColorGradient.of("#00ffff", "#ff00ff").component("Sword"))
                .lore(Component.text("Click to buy"))
                .build(),
        click -> {
            click.player().sendMessage("Bought sword.");
            click.closeNextTick();
        }
).slot(
        15,
        ItemBuilder.of(Material.BARRIER)
                .name(Component.text("Close"))
                .build(),

context.menus().open(player, menu);
Menus should use closeNextTick() and openNextTick(...) when changing inventories from inside click handlers.

Custom Item API

Custom items are plugin-defined item behaviors tracked by CustomItemService. Use them for special items with requirements, cooldowns, and interactions.

public final class MagicSwordItem implements CustomItem {

    @Override
    public String id() {
        return "magic_sword";
    }

    @Override
    public ItemStack create() {
        return ItemBuilder.of(Material.DIAMOND_SWORD)
                .name(ColorGradient.of("#00ffaa", "#ff00ff").component("Magic Sword"))
                .lore(Component.text("A custom KaraAPI item."))
                .build();
    }

    @Override
    public void onAttack(CustomItemAttack event) {
        event.damage(event.event().getDamage() + 4.0);
        event.player().sendMessage(Component.text("Magic hit!"));
    }
}
context.customItems().register(new MagicSwordItem());

player.getInventory().addItem(
        context.customItems().create("magic_sword")
);

boolean isMagicSword = context.customItems().is(item, "magic_sword");

Custom items are tagged using the item's persistent data container.

Registry API

Use RegistryService for ID-based object registries.

MutableRegistry<Menu> menus = context.registries().getOrCreate("menus");

menus.register("shop", shopMenu);

Menu shop = menus.get("shop");
context.menus().open(player, shop);

Create any custom registry:

MutableRegistry<Ability> abilities = context.registries().getOrCreate("abilities");

abilities.register("dash", new DashAbility());

Storage API

Use storage repositories for plugin-owned persistent data.

Example data class:

public record PlayerData(
        UUID id,
        int coins
) {
}

Codec:

StorageCodec<PlayerData> codec = new StorageCodec<>() {

    @Override
    public void write(ConfigurationSection section, PlayerData value) {
        section.set("uuid", value.id().toString());
        section.set("coins", value.coins());
    }

    @Override
    public PlayerData read(ConfigurationSection section) {
        return new PlayerData(
                UUID.fromString(section.getString("uuid")),
                section.getInt("coins")
        );
    }
};

Repository:

Repository<UUID, PlayerData> repository = context.storage().yamlRepository(
        "profiles",
        "profiles",
        UUID::toString,
        UUID::fromString,
        codec
);

Save/load:

repository.save(
        player.getUniqueId(),
        new PlayerData(player.getUniqueId(), 100)
);

PlayerData data = repository.load(player.getUniqueId())
        .orElse(new PlayerData(player.getUniqueId(), 0));
plugins/YourPlugin/profiles/<uuid>.yml

Profile API

Profiles are cached objects backed by a repository.

ProfileCache<PlayerData> profiles = context.profiles().create(
        "players",
        repository,
        uuid -> new PlayerData(uuid, 0)
);

PlayerData data = profiles.getOrLoad(player.getUniqueId());

profiles.save(player.getUniqueId());

profiles.saveAndUnload(player.getUniqueId());

profiles.saveAll();

ProfileService should own profile caches so shutdown can save and unload them correctly.

Requirement API

Requirements are reusable checks for commands, menus, items, regions, abilities, and actions.

Requirement<Player> canUse = Requirements.all(
        Requirements.world("world"),
        Requirements.predicate(
                player -> player.getLevel() >= 10,
                "You need level 10."
        )
);

RequirementResult result = canUse.check(player);

if (result.denied()) {
    player.sendMessage(result.message());
    return;
}

Register reusable requirements:

context.requirements().register(
        "level_10",
        Requirements.predicate(
                player -> player.getLevel() >= 10,
                "You need level 10."
        )
);

Requirement<Player> level10 = context.requirements().get("level_10");

Region spawn = new CuboidRegion(

if (context.regions().contains("spawn", player.getLocation())) {

List<Region> regions = context.regions().at(player.getLocation());

Event Bus

KaraAPI includes a typed event bus for internal and host-plugin events that should not be raw Bukkit events.

public record CoinsChangedEvent(
        UUID playerId,
        int oldCoins,
        int newCoins
) implements Event {
}

context.events().listen(CoinsChangedEvent.class, event -> {
    context.hostPlugin().getLogger().info(
            "Coins changed: " + event.oldCoins() + " -> " + event.newCoins()
    );
});

context.events().publish(new CoinsChangedEvent(player.getUniqueId(), 100, 150));

Cancellable Event Bus Events

Use cancellable events when listeners need to veto an internal action.

public final class AbilityUseEvent implements CancellableEvent {

    private final Player player;
    private boolean cancelled;

    public AbilityUseEvent(Player player) {
        this.player = player;
    }

    public Player player() {
        return player;
    }

    @Override
    public boolean cancelled() {
        return cancelled;
    }

    @Override
    public void cancelled(boolean cancelled) {
        this.cancelled = cancelled;
    }
}

Effect API

Effects describe what should happen: geometry, particles, sounds, ambient sound, timing, audiences, and running handles.

NamespacedKey key = new NamespacedKey(context.hostPlugin(), "spell_circle");

Effect effect = Effects.effect(key)
        .duration(60)
        .particles("outer-ring", layer -> layer
                .geometry(Geometry.circle(15.0))
                .style(ParticleStyles.dust(Color.RED, 1.2f))
                .amount(220)
        )
        .particles("triangles", layer -> layer
                .geometry(
                        Geometry.repeatAroundCircle(
                                Geometry.regularPolygon(3, 1.2),
                                12,
                                14.0,
                                RepeatOrientation.FACING_CENTER
                        )
                )
                .style(ParticleStyles.flame())
                .amount(180)
        )
        .sound("cast", sound -> sound
                .sound(Sound.ENTITY_EVOKER_CAST_SPELL)
                .volume(0.8f)
                .pitch(1.15f)
        )
        .ambient("hum", ambient -> ambient
                .sound(Sound.BLOCK_BEACON_AMBIENT)
                .from(0)
                .to(60)
                .every(20)
                .volume(0.25f)
                .pitch(1.0f)
        )
        .build();

context.effects().registerEffect(effect);

EffectHandle handle = context.effects().play(key, player.getLocation());

handle.cancel();

Important effect concepts:

Concept Purpose
EffectA complete described effect definition.
EffectBuilderBuilds an effect with duration and components.
ParticleLayerSpawns particles from a geometry source.
SoundLayerPlays a sound at a specific tick.
AmbientSoundLayerRepeats sound over a tick range.
GeometryProvides reusable circle, line, polygon, star, spiral, scatter, transform, rotate, and repeat helpers.
EffectAudienceControls who receives the effect output.
EffectHandleCancels a running effect.

Folia Scheduler Adapter

Use SchedulerService as the public entry point for scheduling. It delegates to the installed scheduler executor.

context.scheduler().sync(() -> {
    // main-thread compatible work
});

context.scheduler().at(location, () -> {
    // region/location-aware work when supported
});

context.scheduler().entity(entity, () -> {
    // entity-aware work when supported
});

if (context.scheduler().folia()) {
    context.hostPlugin().getLogger().info("Running with Folia-aware scheduling.");
}

Host plugins should not normally import from the Paper scheduler adapter package. Keep scheduling calls behind api.scheduler.

Runtime Binding Updates

The current runtime binds core services through the runtime service installer and exposes them through CoreServices, BootstrapContext, and PluginHandle.

CoreServiceInstaller creates the public services.
PaperAdapterInstaller connects Paper-specific implementations.
CoreServices groups the initialized services.
BootstrapContext exposes services during module boot.
PluginHandle exposes services after boot.
KaraRuntime owns boot and shutdown coordination.

When adding a new managed service, update the service installer, context record, handle accessors, and cleanup behavior together.

Best Practices

  • Boot once in onEnable() and shut down once in onDisable().
  • Register runtime state through KaraAPI services when possible.
  • Keep raw Paper/Bukkit calls near the edge of your plugin.
  • Use ServiceContainer for services, not content registries.
  • Use RegistryService for ID-based plugin content.
  • Use MessageService for rendered components.
  • Use UiService for player-facing output.
  • Use local placeholders for your own message data.
  • Use PlaceholderAPI only for external placeholders or public expansion exposure.
  • Use closeNextTick() and openNextTick(...) in menus when changing inventories from click handlers.
  • Use SchedulerService or TaskService, not direct Bukkit scheduler calls.
  • Keep lifecycle cleanup in mind for tasks, recipes, menus, listeners, profiles, regions, custom items, and effects.

Use ServiceContainer for services

context.services().bind(EconomyService.class, new EconomyService(repository));

EconomyService economy = context.service(EconomyService.class);

Use RegistryService for content registries

MutableRegistry<Ability> abilities = context.registries().getOrCreate("abilities");

abilities.register("dash", new DashAbility());
abilities.register("blink", new BlinkAbility());

Use MessageService for rendered components

Component message = context.messages().component(
        player,
        "<prefix> <green>Coins: <coins></green>",
        PlaceholderSet.empty().add("coins", 250)
);

Use UiService for output

context.ui().chat(player, message);
context.ui().actionBar(player, Component.text("Ready"));

Use local placeholders for your own messages

PlaceholderSet placeholders = PlaceholderSet.empty()
        .add("player", player.getName())
        .add("coins", economy.balance(player));

context.messages().send(player, MyMessages.COINS, placeholders);

Use PlaceholderAPI only for external placeholders

Local placeholders are faster and simpler for your own plugin's messages. PlaceholderAPI is best used when you need data from other plugins or when you want to expose your own data to other plugins.

Use closeNextTick and openNextTick in menus

click -> {
    click.player().sendMessage("Opening next page...");
    click.openNextTick(nextMenu);
}

Quick Full Example

This example shows a small plugin that boots KaraAPI, registers config/messages, a command, a listener, and a repeating task.

public final class ExamplePlugin extends JavaPlugin {

    private PluginHandle handle;

    @Override
    public void onEnable() {
        this.handle = KaraAPI.boot(this, new ExampleModule());
    }

    @Override
    public void onDisable() {
        if (handle != null) {
            handle.shutdown();
        }
    }
}

public final class ExampleModule implements PluginModule {

    @Override
    public void configure(BootstrapContext context) {
        context.configs().main();
        context.configs().config("messages.yml");

        context.commands().register(
                Commands.command("example")
                        .playerOnly()
                        .executes(command -> {
                            Player player = command.player();
                            context.messages().send(
                                    player,
                                    MessageKey.of("messages.welcome", "<green>Hello <player></green>"),
                                    PlaceholderSet.empty().add("player", player.getName())
                            );
                            return CommandResult.success();
                        })
                        .build()
        );

        context.listeners().register(new Listener() {

            @EventHandler
            public void onJoin(PlayerJoinEvent event) {
                context.ui().chat(
                        event.getPlayer(),
                        "<green>Welcome <player></green>",
                        PlaceholderSet.empty().add("player", event.getPlayer().getName())
                );
            }
        });

        context.tasks().timer("example-announcer", 0L, 1200L, () -> {
            context.hostPlugin().getLogger().info("Example task is still running.");
        });
    }
}
